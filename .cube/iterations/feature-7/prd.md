# 迭代 7 PRD：爽点事件与投票机制

## 1. 功能概述

本次迭代在当前 `/discussion/[sessionId]` 会话详情页内实现“爽点事件与投票机制”，让多角色讨论从普通消息流升级为包含冲突、站队、投票、反转的可参与讨论体验。

本迭代包含以下功能点：

1. 在讨论消息流中展示 EventCard，支持 `slap` 打脸、`camp` 站队、`vote` 投票、`reverse` 反转四类事件。
2. 支持工具栏 `#` 或用户投票指令在当前 session 中主动触发投票事件。
3. 支持用户在 Vote Grid 中点击投票选项，并更新投票状态。
4. 支持基于消息历史、角色立场、关键词和 Director 决策生成事件检测结果。
5. 支持事件插入当前会话消息流，并与普通消息、邀请卡视觉区分。
6. 支持事件记录、投票记录和事件结果随当前会话持久化恢复。
7. 支持事件结果被 Director / Scheduler 消费，用于主持人解释、继续讨论或邀请用户参与。
8. 在模板页事件 Tab 展示模板支持的事件规则，但不展示当前会话的事件实例。

## 2. Functional Requirements

### 2.1 EventCard 与消息流展示

**FR-001（P0）展示事件卡**

- 功能描述：系统应在当前 `/discussion/[sessionId]` 的消息流中展示事件卡，事件卡与普通角色消息、用户消息、邀请卡有明确视觉区分。
- 输入：当前 session 的消息流中包含事件消息或可关联的事件记录。
- 输出：消息流按时间顺序展示 EventCard，卡片展示事件类型、标题、描述、参与角色、状态和必要 payload 内容。
- 异常处理：事件 payload 缺少非关键展示字段时，卡片仍展示事件标题和描述；事件数据不可渲染时展示“事件加载失败”，不得阻断普通消息流。

**FR-002（P0）支持四类事件类型**

- 功能描述：EventCard 必须支持 `slap`、`camp`、`vote`、`reverse` 四类事件。
- 输入：事件记录中的 `eventType`。
- 输出：
  - `slap` 展示反驳双方、被反驳观点和反驳理由。
  - `camp` 展示不同阵营、阵营角色和立场摘要。
  - `vote` 展示投票问题、选项、票数和角色阵营。
  - `reverse` 展示反转前提、新变量和讨论影响。
- 异常处理：未知事件类型展示为通用事件卡，并提示事件类型暂不支持。

**FR-003（P0）事件插入当前会话消息流**

- 功能描述：事件触发后必须插入当前 session 的消息流，不得写入其他会话或全局事件列表。
- 输入：`sessionId`、事件记录、关联消息 ID。
- 输出：当前会话消息流出现对应 EventCard，刷新或恢复会话后仍可看到该事件。
- 异常处理：若 session 不存在，用户看到“会话不存在”；若事件不属于当前 session，提示事件不存在并刷新当前消息流。

**FR-004（P1）事件卡不破坏滚动体验**

- 功能描述：新增事件卡时应保持讨论页滚动体验稳定。
- 输入：用户当前是否停留在消息流底部、事件新增位置。
- 输出：用户位于底部时自动滚动到新事件；用户正在查看历史消息时不强制抢滚动。
- 异常处理：滚动定位失败时保持当前消息流可读，不弹出阻断提示。

### 2.2 投票事件与 Vote Grid

**FR-005（P0）展示投票事件卡**

- 功能描述：投票事件应以 Vote Grid 形式展示投票问题、选项、票数和各选项关联角色阵营。
- 输入：`vote` 事件 payload，包括问题、选项、票数和阵营角色。
- 输出：投票卡展示两个或多个可选项、当前票数、选项阵营角色头像或简称。
- 异常处理：没有投票选项时展示“暂无可投票选项”，并禁用投票操作。

**FR-006（P0）用户提交投票**

- 功能描述：用户点击 Vote Grid 中某个选项后，应在当前 `sessionId + eventId` 下提交投票并更新卡片状态。
- 输入：`sessionId`、`eventId`、`optionId`、用户身份。
- 输出：投票成功后，该选项显示已选中状态，票数和领先选项更新。
- 异常处理：
  - 事件不存在时提示“事件不存在”，并刷新消息流。
  - 非投票事件被投票时提示“该事件不可投票”。
  - 选项不存在时提示“选项已失效”，并刷新事件卡。
  - 投票已关闭时展示最终结果，不允许继续提交。
  - 网络或保存失败时恢复原投票 UI，并提示“投票失败，请稍后重试”。

**FR-007（P0）投票重复提交控制**

- 功能描述：同一 `sessionId + eventId + voterType + voterId` 只能有一个有效投票记录。
- 输入：重复提交或重试提交的投票请求。
- 输出：重复提交同一选项返回已有投票结果，不重复增加票数；默认不允许切换选项。
- 异常处理：重复提交不同选项且不允许切换时，保持已有投票状态并提示用户已投票；若事件允许切换选项，则更新原投票记录，不新增重复票。

**FR-008（P1）投票结果推动讨论**

- 功能描述：用户投票成功后，系统应能输出投票结果摘要，并为后续调度提供主持人解释或继续讨论提示。
- 输入：投票结果、领先选项、当前讨论阶段。
- 输出：下一步讨论可以由主持人解释投票结果，或由 Scheduler 选择相关角色回应。
- 异常处理：如果无法生成调度提示，投票结果仍正常展示，讨论按原有流程继续。

### 2.3 手动触发事件

**FR-009（P0）工具栏 `#` 触发投票事件**

- 功能描述：用户在讨论页工具栏点击 `#`，或输入“触发投票 / 现在投票”等投票指令后，应在当前 session 中创建投票事件。
- 输入：当前 `sessionId`、用户指令、可选投票问题和选项。
- 输出：当前消息流新增投票 EventCard，主持人可解释投票目的。
- 异常处理：触发失败时提示“事件触发失败”，讨论继续；触发频率过高时提示稍后再试，不创建重复事件。

**FR-010（P1）支持手动触发非投票事件**

- 功能描述：系统应支持通过 Director 或内部触发请求创建 `slap`、`camp`、`reverse` 事件。
- 输入：事件类型、触发原因、关联消息、参与角色和 payload。
- 输出：当前消息流新增对应事件卡。
- 异常处理：payload 不满足该事件最低展示要求时，返回创建失败提示，不插入损坏事件卡。

### 2.4 事件检测闭环

**FR-011（P0）打脸事件检测**

- 功能描述：系统应根据最近消息中的明确反驳词或指向前序观点的反驳关系检测打脸事件。
- 输入：当前 session、讨论阶段、最近消息历史、角色信息。
- 输出：当最近 5 条角色消息中出现高置信度反驳时，生成 `slap` 事件候选或事件记录。
- 异常处理：低置信度结果只作为候选，不自动插入消息流。

**FR-012（P0）站队事件检测**

- 功能描述：系统应在多个角色围绕同一问题形成不同立场时检测站队事件。
- 输入：最近一轮角色发言、支持/反对/保守/激进等立场信号。
- 输出：形成两组以上阵营时，生成 `camp` 事件候选或事件记录。
- 异常处理：角色立场无法明确归类时，不自动插入站队事件。

**FR-013（P0）投票事件检测**

- 功能描述：系统应在用户指令、Director 判断争论多轮无结论、或消息中连续出现“无法定夺 / 各有利弊 / 需要选择”等信号时触发投票事件候选。
- 输入：用户意图、Director 决策、消息历史、当前讨论阶段。
- 输出：生成 `vote` 事件候选或事件记录。
- 异常处理：自动投票触发必须经过频率限制；不满足触发条件时不插入事件卡。

**FR-014（P1）反转事件检测**

- 功能描述：系统应在出现“如果前提变化 / 反过来看 / 新变量 / 极端情况”等反转信号，或 Director 主动触发时生成反转事件。
- 输入：消息历史、Director 决策、反转关键词。
- 输出：生成 `reverse` 事件候选或事件记录。
- 异常处理：纯关键词触发置信度不足时，只记录候选，不插入消息流。

**FR-015（P0）EventDetector 边界**

- 功能描述：事件检测应独立于 UI，输入为 session、state、messageHistory、intent 或 director hint，输出为事件检测结果。
- 输入：引擎或服务层传入的讨论上下文。
- 输出：标准化事件检测结果，包括是否触发、事件类型、置信度、原因、参与角色、关联消息和 payload。
- 异常处理：检测失败时返回未触发结果和失败原因，不抛出导致讨论中断的错误。

### 2.5 事件频率限制

**FR-016（P0）同类事件冷却**

- 功能描述：同一 session 中同类事件连续触发间隔不得少于 3 条角色或主持人消息。
- 输入：当前事件类型、当前 session 的历史事件和消息计数。
- 输出：未满足冷却条件时返回限频结果，不创建事件。
- 异常处理：用户手动触发被限频时，展示稍后再触发的提示，不影响讨论继续。

**FR-017（P1）总事件密度限制**

- 功能描述：最近 10 条消息中事件卡不应超过 3 张，避免事件刷屏。
- 输入：当前 session 最近消息列表。
- 输出：超出密度限制时不插入新事件，并返回限频原因。
- 异常处理：被限频的低优先级候选可丢弃或仅记录，不展示给用户。

### 2.6 Director / Scheduler 消费事件结果

**FR-018（P1）Director 消费事件结果**

- 功能描述：事件创建或投票完成后，Director 可根据事件结果决定继续讨论、邀请用户或触发主持人解释。
- 输入：事件结果、当前讨论阶段、最近消息。
- 输出：Director 产生后续动作建议，但不替代已有收束总结职责。
- 异常处理：Director 无法消费事件结果时，讨论按原调度继续。

**FR-019（P1）Scheduler 消费投票提示**

- 功能描述：投票完成后，Scheduler 可优先选择主持人解释投票结果，或选择与领先/落后选项相关的角色继续发言。
- 输入：投票结果、领先选项、阵营角色。
- 输出：后续发言顺序体现投票结果影响。
- 异常处理：若角色不存在或不可发言，回退到原调度策略。

### 2.7 模板页事件规则展示

**FR-020（P2）模板事件 Tab 展示事件规则**

- 功能描述：模板页事件 Tab 应展示模板支持的事件类型与触发规则说明。
- 输入：模板中的事件规则配置。
- 输出：用户可看到该模板支持打脸、站队、投票、反转等事件规则。
- 异常处理：模板未配置事件规则时展示空状态，不影响使用模板发起讨论。

## 3. Non-Functional Requirements

**NFR-001（P0）会话隔离**

事件检测、事件创建和投票提交必须绑定当前 `sessionId`；任何事件或投票不得跨 session 读取、写入或展示。

**NFR-002（P0）持久化与恢复**

EventRecord、VoteRecord、事件关联消息和投票结果必须随会话保存；刷新页面或从会话页恢复当前 session 后，应恢复事件卡和投票状态。

**NFR-003（P0）幂等性**

投票提交必须支持重复请求去重；同一投票人重复提交不得导致票数重复累加。

**NFR-004（P0）可测试性**

事件检测、频率限制、投票幂等、消息流插入和 session 隔离必须可通过自动化测试验证；EventDetector 不依赖 React UI 状态。

**NFR-005（P1）讨论连续性**

事件检测、事件创建或投票失败不得中断普通讨论流程；用户应看到可理解的提示，消息流仍可继续发送和推进。

**NFR-006（P1）交互响应**

用户点击投票后应及时看到反馈；若采用乐观更新，失败时必须回滚到服务端或持久化层确认状态。

**NFR-007（P1）可解释性**

自动触发的事件应包含可展示或可调试的触发原因，便于用户理解“为什么出现这张事件卡”。

**NFR-008（P2）兼容移动端原型体验**

EventCard、Vote Grid、邀请卡和工具栏 `#` 的交互应符合移动端原型中的讨论页布局和视觉层级。

## 4. 验收标准

### 4.1 EventCard 与消息流

- 对应 FR-001：当前会话消息流中能展示 EventCard，且视觉上区别于普通消息和邀请卡。
- 对应 FR-002：四类事件 `slap`、`camp`、`vote`、`reverse` 均有可渲染状态。
- 对应 FR-003：事件只插入当前 `/discussion/[sessionId]` 的消息流；切换到其他 session 不显示该事件。
- 对应 FR-004：新增事件卡不破坏用户查看历史消息的滚动位置；位于底部时可自动滚动到新事件。

### 4.2 投票闭环

- 对应 FR-005：投票事件卡展示问题、选项、票数和角色阵营。
- 对应 FR-006：用户点击投票选项后，已选状态、票数和结果更新。
- 对应 FR-007：同一用户重复提交同一投票不会重复增加票数；重复提交不同选项按规则拒绝或更新原记录。
- 对应 FR-008：用户投票后，后续讨论至少能出现主持人解释或调度提示体现投票结果。

### 4.3 手动触发事件

- 对应 FR-009：用户在讨论页点击工具栏 `#` 或输入投票指令后，当前消息流生成投票事件卡。
- 对应 FR-010：Director 或内部触发请求可以创建非投票事件；无效 payload 不插入损坏事件卡。

### 4.4 事件检测与限频

- 对应 FR-011：最近消息出现明确反驳时，可生成打脸事件候选或事件卡。
- 对应 FR-012：多个角色形成不同立场时，可生成站队事件候选或事件卡。
- 对应 FR-013：争论多轮无结论或用户触发投票时，可生成投票事件。
- 对应 FR-014：出现反转信号或 Director 主动触发时，可生成反转事件候选或事件卡。
- 对应 FR-015：EventDetector 可独立单测，不依赖 UI 组件或浏览器状态。
- 对应 FR-016：同一 session 同类事件连续触发间隔少于 3 条角色/主持人消息时被限频。
- 对应 FR-017：最近 10 条消息中事件卡超过 3 张时，新事件不会继续刷屏插入。

### 4.5 Director / Scheduler 与模板页

- 对应 FR-018：事件结果可被 Director 消费，产生继续、邀请用户或主持人解释建议。
- 对应 FR-019：投票结果可影响 Scheduler 后续发言选择或主持人解释。
- 对应 FR-020：模板页事件 Tab 可展示模板支持的事件规则，但不展示当前会话实例事件。

### 4.6 端到端验收

- 从会话页进入某个当前 session 后，用户可触发投票事件并完成投票。
- 从首页进入新讨论后，用户可通过讨论页工具栏 `#` 生成投票事件。
- 刷新或恢复会话后，事件卡和投票状态仍存在。
- 事件触发失败、投票失败、事件限频时均有提示，讨论输入和普通消息流仍可继续使用。

## 5. Out of Scope

以下内容不属于本迭代范围：

1. Embedding 或复杂语义冲突检测。
2. 多轮 LLM 裁判模型或复杂仲裁机制。
3. 事件运营后台、事件数据分析后台或模板运营系统。
4. 模板事件规则编辑器；本迭代只要求模板页展示事件规则。
5. 多设备同步、服务端数据库迁移或账号级投票身份系统。
6. 完整导出格式中的事件统计细节；事件随会话导出可在后续数据闭环迭代完善。
7. 改造底部导航结构；真实事件仍发生在 `/discussion/[sessionId]`，不新增独立讨论一级 Tab。
8. 替代迭代 6 已实现的邀请、收束和总结职责；本迭代只让事件结果可被 Director / Scheduler 消费。

## 6. 依赖说明

- 依赖当前已有 `/discussion/[sessionId]` 会话详情页、消息流、邀请卡、工具栏快捷指令、会话恢复能力。
- 依赖讨论引擎已有 state machine、intent、scheduler、director 基础能力。
- 依赖服务层或仓储层能按 session 保存和读取消息、事件与投票状态。
- UI 验收以 `docs/prototype/zhinang_mobile_prototype_fixed.html` 中讨论页 EventCard、Vote Grid、邀请卡和工具栏 `#` 交互为基线。
